Session 074 - the hold is authored at run time from the weapon's sockets
=================================================================================

1. Does SM_A88 have a vertical foregrip?  NO.

   Two independent measurements, both against the shipped asset:
     - ADFRC_EF88_MLOD.blend memory points, measured ahead of trigger_axis:
         gl  +17.3 cm    gl_axis        +27.2 cm    gl_cartridge_axis +21.9 cm
         gl_lock_axis  +12.7 cm            muzzle_ugl_pos  +31.6 cm
       All of them 4-5 cm BELOW the bore: grenade-launcher ATTACHMENT proxies. There is no
       grenade-launcher geometry in LOD0 at all.
     - SM_A88.fbx, 78615 verts, 80.22 cm long x 9.77 x 25.41. Every vertex more than 2 cm
       below the bore line lies in x = -35.9 .. +9.1 cm - the stock, pistol grip, magazine
       and trigger guard. From +9.1 cm to the muzzle (+42.4 cm) NOTHING is more than 0.9 cm
       below the bore.
   So the fore-end is a plain tube handguard with a top rail, and the hand surface runs from
   about +9 cm to +30 cm ahead of the trigger. The existing LeftHandGrip socket at +21.9 cm
   (10.3 cm left of the bore) sits mid-handguard, which is right. GRIP_CLIPS still names
   EF88_Vg_static, but "Vg" names the handAnim clip, not the gun; it supplies position only.

2. The frame is built at RUN TIME, not carried through the FBX.

   The socket-rotation route was reverted. Its authored frame came back in game with the thumb on
   (0,0,-1) while the bore at that socket is (0.874,0.388,0.291). This file first blamed the FBX
   exporter for transposing the empty's rotation; that was wrong. Session 073 (the parallel session)
   read the matrix layout and found the transpose was OURS: adfrc_grip.hold_frame_rotation returns
   rows whose columns are the hand axes, mathutils.Matrix() also takes rows, and the .transposed()
   added in 520dc043 turned an already-correct rotation into its inverse. No rotation crosses the
   export in this design, so the question is moot here - but the blame was wrong and is corrected.
   Positions survive the round trip exactly, so FSSHandIK::BuildGripHold builds the frame from them:
       forward = muzzle - RightHandGrip
       up      = the weapon component's own up, orthogonalised against forward
       right   = up x forward            (UE satisfies F x R = U, so U x F = R)
       thumb   = forward, palm = up tilted PalmTiltDeg towards right, finger = palm x thumb

   Sign of right, checked against the weapon itself, not derived: the ejection port is on the
   shooter's right and the left hand grip on the shooter's left. Every sample below:
       eject_on_right=1  left_grip_on_left=1  eject_dot_right=+1.625  grip_dot_right=-9.492

3. Handedness - the bug the 0.0 deg residual hid.

   A LEFT hand has palm = thumb x finger, so palm x finger = -thumb: its own (palm, finger,
   thumb) triad is LEFT-handed and is not a rotation. The first version of this work used
   finger = thumb x palm, which is a RIGHT hand's relation, and measured the palm as
   finger x thumb to match. It reported residual 0.0/0.0/0.0 on every sample - a mirrored
   frame still matches a mirrored target - and rendered the back of a closed fist on the
   handguard. Correcting both sides dropped the pre-offset error from 124.8/125.4 deg to
   55.2/54.6 deg against the arms' own clip pose, and the hand now wraps the tube.
   ToHandRotation is therefore MakeFromXY(Palm, Finger): +X palm, +Y finger, +Z the
   back-of-hand axis. The per-skeleton offset is unaffected, because it is solved against the
   measured frame either way.

7. The per-weapon data path, and a silent failure worth knowing about.

   GripPalmTiltDeg is a TMap, and its ini form is unforgiving:

       +GripPalmTiltDeg=(A88=30.0)     -> LogObj: Error: ... import failed for
                                           GripPalmTiltDeg ... and the property stays EMPTY
       +GripPalmTiltDeg=(("A88",30.0)) -> imports cleanly

   The failure is quiet. The engine logs it once and carries on, so every weapon silently falls back to
   DefaultPalmTiltDeg and nothing else looks wrong. It was caught by setting the A88 row to a
   distinctive 45 and reading the realised tilt back: with the broken form the game still reported
   palm_tilt=30.0 deg, and with the fixed form it reported 45.0 deg (Saved/Logs/SS_cfg_probe2.log).
   A per-weapon value that appears to be ignored should be checked against "import failed for" in the
   log before the code is suspected.
